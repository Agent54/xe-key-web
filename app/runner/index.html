    Nothing here is installed, and nothing asks for permission. A link opens a signed app in a sandbox it cannot send anything out of.

    1. Resolve. A readable name such as key-web://localpad.lukeinth.at/ is looked up on its rail, then checked against the key pinned the first time you used it.
    2. Fetch. Bytes arrive from a mirror, a swarm of peers, a file, or the local cache.
    3. Verify. The Ed25519 signature is checked right here, in this page, before any byte is parsed.
    4. Derive. The origin is the signing key, whatever name led to it. Same key, same origin, same data.
    5. Run. Tier 0: no network of any kind until you grant one narrow capability.

            Readable names and resolver rails

            A name like key-web://localpad.lukeinth.at/ is looked up on a rail, which answers with a record signed by the publisher: "this name is this key". The rail is never trusted for that. The first key a name resolves to is pinned here, and after that the pin decides. A rail can be down, or taken over, and a pinned name still means what it meant.

            Petname book

            A signature tells you which key published an app. It cannot tell you who that is. A petname is a name you chose, kept on this machine, bound to exactly one key.

            Impersonation test

            An attacker copies LocalPad, signs it with their own key and calls it “LocalPad”. The signature is perfectly valid. Only a petname catches it.

            Key rotation, committed in advance

            LocalPad's signed bundle carries the hash of the only key allowed to take over. A rotation certificate must be signed by the old key, name a new key matching that hash, and be signed by the new key too.
